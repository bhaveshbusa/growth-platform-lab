# RFC 0002: Event Contracts and Validation

## Status

Accepted

## Context

Phase 1 produced a reviewed tracking plan and a gateway that collects nothing. The plan is machine-readable so that later phases can **derive** validation from it; deriving it is this phase's job.

The temptation is to hand-write validators — a DTO class per event, or a JSON Schema per event maintained beside the plan. Both duplicate the plan, and duplicates diverge: the plan says `duration_seconds`, the DTO says `duration`, and now there are two answers to "what is a valid `lesson_completed`?" with no way to tell which one the warehouse believes.

This phase also has to decide what "invalid" means to the rest of the system. From phase 3 the gateway dead-letters what it cannot accept, and a dead-letter queue nobody can group by cause is a queue nobody triages. So rejection needs a small, stable vocabulary that survives being written to a stream and read by a human at 02:00.

## Decision

### The plan compiles into contracts; nothing is written per event

`libs/event-contracts` loads `docs/tracking-plan.yaml`, refuses to compile a plan it cannot trust, and builds one contract per `name@version`. Adding an event to the plan makes it acceptable; removing it stops it being acceptable. No file in the library mentions `lesson_completed`.

The loader is strict about the plan itself — unknown property types, unknown PII classes, missing descriptions and enums without values are errors — because a plan that half-parses produces contracts that half-validate.

### The envelope is closed, and separate from the properties

Every event travels in the same envelope: `message_id`, `event`, `version`, `sent_at`, `anonymous_id`, optional `user_id`, `source`, `consent`, optional `context`, and `properties`. The envelope belongs to the platform, the properties belong to the event.

Both are **closed sets**: unknown properties and unknown envelope fields are rejected rather than dropped. Dropping is friendlier and worse — the client keeps sending data nobody reviewed and nobody stores, and the person who added it believes it is being collected. Refusing produces an actionable rejection instead of a silent hole.

`message_id` exists now although nothing deduplicates yet: idempotency (phase 3) needs a key that the _client_ chose, and retrofitting one after clients ship is the problem phase 1 warned about.

### Contracts describe the shape of consent, not the decision

The envelope must carry a boolean for every purpose the plan declares — no more, no fewer. A missing purpose is a malformed envelope, because "we do not know whether this learner agreed to marketing" is not a state the pipeline can carry.

Whether a `false` decision suppresses the event is deliberately **not** decided here; that is enforcement, and enforcement belongs with the write path in phase 3. Contracts answer "is this well-formed and planned?", the gateway answers "may we keep it?".

### Rejection reasons are a closed taxonomy

Nine reasons, chosen so that each one implies a different fix by a different person:

| Reason                          | Who fixes it                                 |
| ------------------------------- | -------------------------------------------- |
| `malformed_envelope`            | the SDK                                      |
| `identity_missing`              | the SDK or the cookie/consent layer          |
| `unknown_event`                 | whoever shipped an unreviewed event          |
| `unknown_event_version`         | a client that outran the plan, or vice versa |
| `server_only_event_from_client` | a trust boundary problem, not a bug          |
| `missing_required_property`     | the instrumentation call site                |
| `unknown_property`              | the tracking plan, or the call site          |
| `property_type_invalid`         | the call site                                |
| `property_value_not_allowed`    | the plan's enum, or the call site            |

Two consequences of that table shape the implementation. Validation reports **every** problem for an event rather than the first, so one rejected batch teaches the whole fix instead of three deploys. And rejections carry a field path and a reason but **never the offending value**, because rejections get logged, and the most common invalid property is an unplanned personal one.

`server_only_event_from_client` is its own reason rather than a generic schema error because it is the only rejection that means someone may be lying to you: `subscription_started` is marked `source: server` in the plan, so a browser claiming money changed hands is refused regardless of how well-formed it is.

### Types are generated from the plan, and drift is a test failure

`libs/event-contracts/src/generated/events.ts` is generated by `pnpm contracts:generate` and checked in: event keys, a union per enum, one interface per event version, the consent purposes, and a fingerprint of the plan. A test regenerates it in memory and fails if the checked-in file differs, so a plan change and its types travel in the same pull request.

The fingerprint covers the plan's _meaning_, not its bytes: reformatting the YAML or editing a comment must not invalidate generated code, while renaming a property must. Publishing that fingerprint from the gateway gives later phases a cheap answer to "which plan version produced this data?".

Checking generated code in is not free — it shows up in diffs. The alternative, generating at build time, means the types nobody regenerated describe last month's plan while the tests pass.

### The gateway publishes contracts and refuses to run without them

`GET /v1/contracts` and `GET /v1/contracts/:name/:version` expose the catalogue, so a client can discover what it may send instead of guessing from a wiki page.

If the plan cannot be compiled, the gateway starts, stays **live**, and reports itself **not ready** with 503 — it does not crash, and it does not start with an empty contract set. A collector with no contract accepts everything, which is a data quality incident with excellent uptime. Reporting 200 with `"status": "not_ready"` would keep the instance in the load balancer, so the status code carries the verdict.

There is still **no write path**: `POST /v1/events` arrives in phase 3 with batching, idempotency, consent enforcement, and dead-lettering. To exercise contracts now, `pnpm contracts:validate <file.json>` runs the same validator over a payload and exits non-zero on rejection.

## Alternatives considered

- **JSON Schema per event, generated from the plan.** Standard, tool-rich, and the right answer if external clients need machine-readable schemas. Rejected for now: it adds a validator dependency and a second artefact to keep in step, and the rejection vocabulary — the part downstream phases actually depend on — would have to be mapped back out of schema error objects.
- **Hand-written `class-validator` DTOs per event.** Idiomatic Nest, excellent editor support, and precisely the duplication this phase exists to avoid; eleven events would become eleven files that may disagree with the plan.
- **Validate with generated TypeScript types only.** Types vanish at runtime. The gateway's input is untrusted JSON, so the check has to exist at runtime; the generated types are for authoring, not for defence.
- **Drop unknown properties instead of rejecting.** What most vendors do, and it keeps clients working; it also silently loses data and hides taxonomy drift until someone asks why a column is empty.
- **Fail startup when the plan will not compile.** Loud and simple, and a common Kubernetes idiom (crash-loop until fixed). Rejected because liveness and readiness then say the same thing, and the more instructive behaviour — live, unready, explaining itself — is the one this project wants to teach.
- **Enforce consent in this phase.** Tempting, since the envelope already carries it; it belongs with the write path, where suppression, dead-lettering and audit live together.

## Consequences

- There is exactly one answer to "what is a valid event?", and it is the plan. Contracts, generated types, the published catalogue, and the CLI are all views of it.
- Adding an event is still a pull request, but now the pull request is small: edit the plan, run `pnpm contracts:generate`, and both validation and types follow.
- Dead-lettering in phase 3 has a vocabulary to write down, and product analytics has a fingerprint to attribute data to.
- Rejection is all-or-nothing per event: there is no partial accept, no coercion, and no "accepted with warnings". That will feel harsh the first time a client sends `score: "92"`.
- The gateway now has a dependency that can make it unready, which is the first honest readiness check in the system and the model for the ones that follow (stream, profile store).
- Deployments must ship `docs/tracking-plan.yaml` alongside the code, or set `TRACKING_PLAN_PATH`. The plan is now runtime configuration, not documentation.
- Nothing is collected yet. Phase 2 can tell you an event is wrong; it cannot yet tell you it happened.
